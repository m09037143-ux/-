## Этап B — схема БД, регистрация, сессии, роли, trial, тарифы

**Работает** (покрыто тестами, `tests/test_auth.py`, `test_tenant_isolation.py`, `test_trial.py`):

  межарендная изоляция проверена тестом (workspace A не видит объекты workspace B).

  уникальный индекс исключает повторную запись; повторный вход/новый браузер
  не сбрасывают срок (тест). `GET /api/v1/access` — единая точка проверки.
- Тарифы: три плана из ТЗ §7 засеяны миграцией; лимиты (`max_flows`,
  `max_sources_per_flow`, `max_news_per_run`, `manual_or_daily_schedule_only`)
  проверяются на сервере при создании/изменении потока (`PLAN_LIMIT`).

**Пока mock / заглушка:**

  в ответе `/auth/forgot-password`; токен в dev/test возвращается в теле ответа
  для локальной проверки, в проде — нет.

  (`POST /orders/{id}/webhook/fake`, только при `PAYMENT_PROVIDER=fake`) существует

**Нужно решение владельца:**

  значения с пометкой `needs_customer_decision: true` в `plans.limits`).

  встроенный в API-хендлер; опрашивает таблицу `scan_jobs` в Postgres

**Нужно решение владельца:**

## Этап D — официальные документы, YandexGPT Pro 5.1, паспорт фактов, ручная проверка

**Работает** (тесты: `test_editorial_workflow.py`, `test_llm_provider.py`):
- `official_documents`/`fact_passports` с раздельными отметками
  `official_reviewed`/`facts_reviewed`; правка черновика, документа или
  паспорта фактов **обнуляет** обе отметки (тест).
- Optimistic locking через `expected_version`/`VERSION_CONFLICT`.
- Полный конвейер состояний `DISCOVERED → NEEDS_REVIEW → READY_FOR_REVIEW →
  APPROVED → PUBLISHED` (и `REJECTED`), утверждение невозможно без документа
  и обеих отметок проверки (`OFFICIAL_SOURCE_MISSING`/`EDITOR_REVIEW_REQUIRED`).
- `YandexGPTPro51Provider`: жёсткая проверка конфигурации (`YANDEX_MODEL_URI`
  обязан совпадать с `gpt://{YANDEX_FOLDER_ID}/yandexgpt-5.1`); без ключа и
  без явного `LLM_FIXTURE_MODE=true` — `LLM_NOT_CONFIGURED`, без тихого
  переключения на другую модель (тест `test_llm_never_silently_swaps_model`).
  Каждый вызов логируется в `llm_calls` (модель/URI, версия промпта,
  request_id, хеш входа, токены, длительность, ошибка) без API-ключа в логе.
  Дневной бюджет токенов на workspace проверяется перед вызовом
  (`LLM_BUDGET_EXCEEDED`). Результат каждого этапа валидируется строгой
  Pydantic-схемой; невалидный JSON → ошибка и `VALIDATION_ERROR`, а не
  готовая публикация.
- ИИ-черновик (`POST /news/{id}/ai/draft`) пишет результат ровно как обычную
  ручную правку — статус остаётся `NEEDS_REVIEW`, отметки проверки не
  выставляются, **утверждение по-прежнему требует человека** (тест).

**Нужно решение владельца:**
- `YANDEX_FOLDER_ID` и `YANDEX_API_KEY` — передать безопасным каналом, не в
  чат и не в репозиторий.
- Фактический тариф YandexGPT Pro 5.1 для расчёта `cost_rub` в `llm_calls`
  (сейчас пишется 0 — стоимость неизвестна без реального контракта).
- Поиск официального документа сейчас **полностью ручной** (редактор вносит
  URL/реквизиты сам) — автоматический подбор официального источника по теме
  не входил в этот проход и не заявлен как обязательный API в ТЗ §12.

## Этап F — подключение HTML-фронтенда

**Выполнено по отдельному запросу пользователя** (изначально отложено по
ТЗ §1, затем явно запрошено). `frontend/index.html` — та же вёрстка/CSS
исходного прототипа без визуальных изменений; `frontend/app.js` — полностью
переписанная логика поверх реального API (`fetch(...,{credentials:'include'})`
+ `X-CSRF-Token`) вместо localStorage. Подробности запуска — README.md,
раздел «Frontend».

Проверено вживую через Playwright (реальный Chromium): полный цикл
регистрация → поток → сбор (настоящий worker) → редактирование → официальный
документ → факты → проверка → утверждение → публикация → публичный
предпросмотр → экспорт XML → тарифы → администрирование (обычный
пользователь и реальный platform_admin отдельно) → выход/повторный вход →
гостевой просмотр. В процессе найдены и исправлены реальные ошибки (не
гипотетические): несовместимый с тарифом «Старт» дефолт периодичности в
мастере настройки потока; несвежий счётчик опубликованных материалов на
странице экспорта; гостевой режим ошибочно требовал входа вместо показа
локального примера; кратковременный неверный экран администрирования до
получения ответа сервера.

**Сознательно не перенесено из прототипа** (см. README «Frontend» и
`AUDIT.md`):
- Экран ввода нового пароля по токену из письма — почта не подключена
  (ТЗ §15); вместо этого в dev/test-окружении форма «Забыли пароль»
  сама предлагает установить новый пароль по токену, который backend
  возвращает только вне production.
- Кнопка «Восстановить примеры» в «Опасной зоне» настроек — необратимо
  затронула бы реальные данные рабочего пространства, показана как текст
  без действия.
- Полноценная роль-специфичная админ-панель для владельцев рабочего
  пространства — экран «Администрирование» в прототипе теперь корректно
  ведёт к настоящему platform-admin API (глобальному, не per-workspace);
  для обычных пользователей показывает честное сообщение об ограничении
  доступа вместо прежнего фиктивного контента.

## Найдено и исправлено при ручном тестировании (после этапа F)

- **Промпты к YandexGPT не просили ответ в JSON, хотя код требовал именно его.**
  Найдено при подключении реального ключа: `_run_stage` парсит ответ модели как
  строгий JSON по Pydantic-схеме (`model_validate_json`), но сами промпты
  («Напиши текст…», «Извлеки факты…») не содержали требования отвечать в JSON —
  любая настоящая модель (не только Yandex) ответила бы связным текстом, и
  каждый реальный вызов падал бы с `VALIDATION_ERROR` независимо от того,
  верен ли ключ. Все четыре промпта (`relevance`, `fact_passport`, `draft`,
  `critique`) теперь явно требуют строгий JSON по указанной схеме; добавлена
  также защита `_strip_markdown_json_fence` на случай, если модель всё равно
  обернёт ответ в ```` ```json ```` — до реального вызова эта защита не
  проверялась ни разу.

- **«Собрано 0 материалов» после повторного сбора выглядело как сбой.**
  Антидубль по ТЗ §9 работает верно (повторный сбор по той же теме не создаёт
  вторых карточек), но UI показывал голое «добавлено материалов — 0»
  неотличимо от «источники ничего не нашли». Найдено вживую (пользователь
  подумал, что сбор не работает, хотя материалы уже были собраны раньше).
  `GET/POST .../scan-jobs` теперь возвращает `duplicate_count` (сколько из
  найденного распознано как дубликат уже собранной истории), фронтенд
  показывает «новых материалов нет — все N уже собраны ранее» вместо голого
  нуля (`tests/test_fixture_source_and_dedupe.py::test_repeated_runs_dedupe_same_story`).

- **Ошибки валидации тела запроса (Pydantic) не приводились к формату API.**
  До правки FastAPI сам отдавал 422 в собственном формате
  `{"detail":[...]}`, минуя `AppError`/`app_error_handler`, — фронтенд не
  умел его разобрать и показывал безликое «Ошибка сервера (422)» (найдено
  вживую на форме регистрации, короткий пароль). Добавлен
  `request_validation_error_handler` (`app/errors.py`), приводящий такие
  ошибки к общему виду `{"error":{"code":"VALIDATION_ERROR","message":...}}`
  с понятным сообщением на русском по каждому полю (`tests/test_auth.py`:
  `test_register_short_password_returns_readable_app_error`,
  `test_register_invalid_email_returns_readable_app_error`).

## Этап G — деплой на Render.com (по запросу пользователя)

`legal-flow/render.yaml` описывает два компонента: API и PostgreSQL
(Redis заводится отдельно вручную — см. `docs/DEPLOY_RENDER.md`,
пошаговая инструкция без использования консоли).

Изначально frontend разворачивался как отдельный Render-сервис (статика),
из-за чего API и frontend оказывались на **разных** поддоменах
`*.onrender.com` — куки сессии были жёстко закреплены за `SameSite=Lax`,
и при межсайтовых запросах браузер не отправлял бы их вовсе (вход не
работал бы после деплоя). Вместо того чтобы просто ослаблять cookie
(`SameSite=none`) под два домена, упрощена сама схема: `app/main.py`
теперь монтирует `frontend/` как статику прямо в FastAPI-приложении
(после всех API-роутов, `StaticFiles(html=True)`) — сайт целиком живёт на
одном домене. Убраны: отдельный Render-сервис под статику,
`FRONTEND_ORIGIN` как обязательная ручная переменная, необходимость
`SameSite=none` (остался безопасный по умолчанию `lax` — настройка
`COOKIE_SAMESITE` в `app/config.py`/`app/cookies.py` сохранена на случай,
если кто-то всё же разнесёт frontend на отдельный домен). Локальный
запуск тоже упростился: `frontend/index.html` (`pp-api-base` теперь
пустой — тот же домен) отдаётся тем же `uvicorn`, отдельный
`python -m http.server 5500` для фронтенда больше не нужен ни локально,
ни на Render.

**Фоновый worker на Render не размещён** — подтверждено на практике при
попытке деплоя: у Render нет бесплатного тарифа для Background Worker
(только платный, от ~$7/мес., карта Render запрашивает сразу для всего
блюпринта, если в нём есть хоть один платный сервис). По решению
владельца — гибридная схема: API/БД/статика на Render, а
`app/worker/runner.py` продолжает работать локально на компьютере
владельца, подключаясь к той же Render-базе по внешнему (External)
адресу вместо локального. Требование ТЗ §4 об «отдельном worker-процессе»
этим не нарушается (worker по-прежнему отдельный процесс, не встроен в
API), но зависимость от включённого компьютера для реального сбора
материалов остаётся — задокументировано явно, не скрыто.

## Этап H — worker переведён с Redis-очереди на опрос Postgres

При настройке гибридной схемы (этап G) обнаружилось на практике: у
бесплатного тарифа Render Key Value (Redis) внешние подключения **вообще
запрещены** («External traffic not allowed»), только доступ из других
сервисов Render по приватной сети. Добавление IP в allowlist не решает
проблему по-настоящему — домашний IP обычно динамический и периодически
меняется.

Вместо этого убрана сама зависимость worker'а от Redis. Раньше
`POST /flows/{id}/scan-jobs` после записи задания в Postgres дополнительно
клал его id в Redis-очередь (`RPUSH`/`LPOP`, `app/worker/queue.py`), а
worker эту очередь вычитывал. Теперь запись в Postgres сама по себе и есть
очередь: `app/worker/runner.py` каждые 0.5с делает
`SELECT id FROM scan_jobs WHERE status='pending' ORDER BY created_at LIMIT 1
FOR UPDATE SKIP LOCKED`. `app/worker/queue.py` удалён, вызов из
`app/routers/flows.py` тоже. `SKIP LOCKED` сразу корректен и при нескольких
worker'ах (на будущее), хотя сейчас предполагается один.

Следствие: worker'у больше не нужен `REDIS_URL` вообще — только
`DATABASE_URL`. Redis остался только у API-процесса, для rate limiting
(`app/services/rate_limit.py`), и не требует внешнего доступа, потому что
API и Redis всегда на одной стороне (оба на Render, или оба локально).

- **Python 3.11**, а не «3.12+» — таково окружение этой сессии; код не
  использует ничего специфичного для 3.12, миграция тривиальна.
- Для фоновой очереди worker опрашивает таблицу `scan_jobs` в Postgres
  напрямую (`SELECT ... FOR UPDATE SKIP LOCKED`), а не Celery/RQ и не
  отдельная очередь в Redis — целиком достаточно для одного типа задачи и
  явно запрошенного «одного отдельного worker'а»; более тяжёлый брокер
  можно подключить позже без изменения контракта API. Изначально была
  собственная Redis-очередь (`RPUSH`/`BLPOP`), но при гибридном деплое
  (worker — локально, API — на Render) выяснилось, что бесплатный Redis
  Render вообще не даёт внешних подключений — см. этап H.
- Добавлен код ошибки `LLM_BUDGET_EXCEEDED` (429), которого нет в списке ТЗ
  §12 — без него требование «бюджет на workspace/день» (ТЗ §10) нечем было
  бы вернуть как осмысленную ошибку API.
